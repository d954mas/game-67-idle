# Neotolis Scene Manager Integration Profile

Status: IMPLEMENTED IN THE DEFAULT TEMPLATE AND TROLLEY GAME; RE-REVIEWED 2026-07-24

Depends on:
[`SCENE-MANAGER-SPEC.md`](SCENE-MANAGER-SPEC.md)

This profile maps the portable manager onto the current template. The manager
does not take ownership of the engine frame, resource manager, raw input,
renderer, or `ui_runtime_begin/end`.

## 1. Frame placement

The existing template order is:

```text
window/devapi/input poll
resource/material step
game update/reactions
graphics begin/pass
world/HUD render
ui_runtime_begin -> immediate UI -> ui_runtime_end
graphics end/present
```

The integrated order is:

```text
1.  nt_window_poll
2.  DevAPI frame/input release
3.  nt_input_poll
4.  nt_resource_step and nt_material_step
5.  increment frame_index
6.  scene_manager_step(manager, frame_index, dt)
7.  scene_manager_update(manager, dt)
8.  remaining game reactions/recording/save
9.  nt_gfx_begin_frame/pass
10. host render systems draw only visible scene membership
11. if ui_runtime_begin(dt):
      scene_manager_build_ui(manager, ui_runtime_ctx())
      build permitted global shell UI
      if scene_manager_input_gated(manager): build host input gate last
      ui_runtime_end()
12. nt_gfx_end_pass/frame and present
```

`ui_runtime_begin/end` stay host-owned because they also manage scratch/font,
Clay input, UI walk, and renderer flush.

All accepted navigation commands are pending until the next manager step.
Preload request bits are also started there. This gives lifecycle mutation one
fixed phase.

## 2. Loading and resources

Typical shared-pack scene:

1. `load_begin` requests/stores mandatory handles.
2. `load_step` checks type-specific readiness and incrementally creates runtime.
3. READY means the first valid runtime is complete.
4. `unload` destroys runtime/bookkeeping; shared engine assets remain resident
   because Neotolis has no per-resource release API.

Readiness examples:

- GPU resource: `nt_resource_is_ready`;
- atlas: wait for atlas, resolve/cache mandatory pages, then wait for pages;
- blob: wait for ready/non-null data, copy persistent data;
- runtime object: game-owned validator.

Known failures log their resource id and assert. Manager load deadlines catch
otherwise endless pending.

Optional dedicated pack:

- mount in `load_begin`, unmount in synchronous `unload`;
- core never remounts that singleton in the same manager step;
- because the host calls `nt_resource_step` before the next manager step,
  publication/deactivation advances before reload;
- build-time manifests, not runtime counts alone, prove pack/asset capacity.

No pack is generated by default.

## 3. Input ownership audit

Every direct game `nt_input`/`g_nt_input` reader must be classified:

- scene gameplay/UI: guarded by `scene_manager_can_process_input`;
- shell/platform: explicitly allowed and must respect
  `scene_manager_input_gated` where relevant.

Migration includes a repository scan and allowlist test so new unguarded game
readers fail CI.

Known template readers requiring attention:

- `sys_move` direct WASD polling;
- native Escape-to-quit before game update;
- `ui_runtime_begin` feeding all pointers to Clay;
- platform lifecycle gesture detection (allowed platform consumer).

Escape-to-quit moves behind manager ownership/gate logic. Clay pointer input is
blocked by the host UI gate below.

## 4. Enforced UI gate

Scene UI modes are INTERACTIVE and PASSIVE.

- stable focused top: INTERACTIVE;
- ordinary below modal: PASSIVE;
- every visible scene during pending/active navigation: PASSIVE.

PASSIVE builders emit full visuals, declare every interactive widget disabled,
and do not act on widget results. This includes `nt_ui_input`, menu/dropdown,
and every keyboard-focus widget. Every previously focused visible input is
redeclared with `enabled=false` on the first passive frame, which makes
`nt_ui_input` clear its focus. An input belonging to a now-hidden scene is not
stepped and its orphan focus is cleared by normal `nt_ui_begin` reconciliation
on the next frame. The public API has no separate host focus-clear call.

Because that rule alone is cooperative, the host declares a full-screen
shell-owned pointer catcher after all scene and global UI whenever
`scene_manager_input_gated()` is true. It is the topmost pointer interaction
surface and has no functional actions. It does not block keyboard, text, or
focus. Global shell widgets are disabled or omitted while gated; merely placing
an enabled keyboard widget below the pointer catcher is insufficient.

Raw keyboard/game input is separately blocked through
`scene_manager_can_process_input`.

Required tests:

- source button cannot fire while target loads;
- global settings/debug button cannot fire through the gate;
- opening press/release cannot activate the new modal;
- enter/exit Escape and backdrop cannot fall through;
- focused modal text input cannot route to a lower scene;
- first stable interactive frame works.

## 5. Modal animation

Show:

1. target reaches READY;
2. history commits and `on_show(args)` builds its presentation state;
3. enter transition steps with manual/game `dt`;
4. after DONE it becomes interactive.

Close:

1. accepted command gates input immediately;
2. visible modal remains PASSIVE during exit;
3. transition completes only after the game animation and
   `nt_ui_modal_result.fully_closed` are complete;
4. `on_hide`, atomic history commit, resume/show callbacks, and cleanup follow
   the core presentation-diff order.

Only the top modal is built. Atomic Back/close never builds intermediate modals.

## 6. Rendering and `keep_loaded`

Current template rendering draws one shared `World`, so migration must choose
and test one explicit mechanism:

- scene entities/components have an active presentation membership toggled by
  `on_show/on_hide`; or
- render systems filter entities by the manager's visible scene ids.

`keep_loaded` retains runtime/resources only. It never implies visible or
renderable.

Scenes do not receive `on_draw`. Exceptional debug rendering stays an explicit
game-host render call after a visibility query.

## 7. Shutdown

Shutdown may occur in any navigation phase:

1. disable DevAPI/navigation mutation and scene consumers;
2. `scene_manager_shutdown` abandons pending/active work, hides current
   presentation, clears preload flags, and calls `unload` once for every
   LOADING/READY scene;
3. host calls `nt_resource_step` so dedicated-pack unmount publication advances;
4. shut down UI/render consumers and the manager object;
5. call `nt_resource_shutdown`.

Tests cover every navigation/transition phase plus visible, hidden
`keep_loaded`, absent preloaded READY, and partially LOADING scenes.

## 8. Separate engine work

Selective activation/unload of individual resources within one `.ntpack` is
outside this feature. It remains an independent engine issue/PR and does not
block V1.
