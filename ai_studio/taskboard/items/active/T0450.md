## What

Числа игры авторятся двумя способами: предметы на Lua (модули, песочница,
Snapshot), прогрессия на JSON плюс питоновский генератор. Разница
историческая — предметы получили Lua-авторинг в E016, прогрессия осталась на
JSON, и их не свели.

**Переиспользуем вычислитель, а не модель предмета.**

### Трек предметом не является

`ITEM_KEYS` — закрытый список (`items_snapshot.py:41-44`): ни `mode`, ни
`currency_def` там нет, а `section != "level_row"` — жёсткий отказ (`:182`).

Хуже: поле в схеме привязано к «виду» всё-или-ничего — обязательно на каждой
строке подходящего вида, отвергнуто на любом другом (`:249-254`), а
кодогенерация выпускает по структуре на вид. Для 60 треков с разными
колонками это либо один вид, где каждый трек обязан объявить все колонки
игры, либо 60 видов с 240 функциями.

И базы расходятся: прогрессия 0-базная (`cost[level]` — цена ухода с `level`,
`cost_count == max_level`), items 1-базный (строка N и есть уровень N).
Плюс `cost[0]` у прогрессии — приобретение, а в items это отдельное
`acquire.cost`.

### Что делаем

**`studio.tracks` — соседнее пространство объявлений рядом с `studio.items`**,
переиспользующее `studio.levels` и `studio.field` без изменений. Манифест
`items.lua.sandbox.v1` переименовывается в `studio.lua.sandbox.v1`, Snapshot
получает секцию `tracks`.

Прогрессия сохраняет свой генератор, свой 0-базный массив цен, свой словарь
колонок и `progression_value_t`. Меняется только вход: не
`content/progression.json`, а секция снапшота.

Это дополнение к items (**MINOR**), а не ломающая правка: ни `ITEM_KEYS`, ни
версия `items.snapshot.v1`, ни формат пакета, ни ABI не трогаются.

### Что реально переиспользуется

Проверено по коду, не по документам:

| нужно треку | есть в песочнице |
|---|---|
| таблица по уровням | `levels.table` (`items_lua_sandbox.py:237`) |
| линейная кривая | `levels.linear` (`:284`) |
| формульная кривая | `levels.generate` (`:240`) — escape hatch на `studio.math`, **не** готовый `exp` |
| именованные колонки | `levels.columns` (`:300`) |
| объявление колонок | `items.extend_schema({ level_row = … })` (`:174`) |
| многопозиционная стоимость | встроенный `cost_to_reach` + `items.costs({ items.cost(ref, n), … })` (`:162-164`, `:812-819`) |

**`field.cost_list` не существует** — единственный конструктор поля это
`field.i64` (`:187`). Он и не нужен: многопозиционная стоимость уже есть как
`cost_to_reach`. Прежняя редакция цитировала концепт-документ как отгруженный
код.

### Float

Лид: делаем float — фиксированная точка навязывает масштаб каждому будущему
числу, это лишняя бухгалтерия. Степень (`pow`) тоже разрешаем: точности
хватает, расхождение слишком мелкое, чтобы его заметить.

Целочисленность зашита в шести местах: `items_lua_sandbox.py:326-331`
(`checked()`), `:702`/`:736`/`:808` (значения колонок, `linear`, строки
таблицы), `:332-354` (`studio_math` — только `add/sub/mul/idiv/min/max`,
float-арифметики нет вовсе), `items_snapshot.py:186-196,256`,
`items_runtime_package.py:223,478-479,555`.

Форма:

- колонка объявляется дробной; целые остаются целыми;
- во float-формулах разрешены `+ − × ÷` и степень;
- политику округления не заводим. Значение считается **на сборке** и
  запекается C-литералом с точностью, гарантирующей обратное чтение; рантайм
  формул не трогает.

Про `pow` и libm: концепт-документ его запрещал из-за платформенной
зависимости младших битов. Лид принял этот риск, и он гасится конструкцией —
значение считается один раз на машине сборки и коммитится литералом, а
дрифт-гейт байт-сверяет результат. Пересчёт на другой машине покажется как
видимый дифф в ревью, а не как тихое расхождение в рантайме.

`features/progression-core/feature.json:8` обещает «baked int64 curve codegen
(zero float in C)» — строка становится ложной, переписать с бампом.

### Пороговая кривая — дыра, которую нашло ревью

`cost_to_reach` строго про стоимость в предметах. Понятия «накопить xp до
порога» в Lua-конвейере **нет**, а карточка игровой миграции требует ранги треком `threshold`
на дельтах и без этого не стартует. Прежняя редакция несла `advance: { cost |
threshold }` и потеряла порог при переписывании под Lua.

`studio.tracks` обязан выражать оба продвижения — стоимость в предметах
(`manual`/`auto`) и порог собственного xp (`threshold`) — формой, где
представим ровно один вариант на режим.

### Границы

**C приватного потребителя мигрирует здесь, контент — нет.** progression-core компилируется
им in-place (`CMakeLists.txt:29-32`), поэтому удаление
`progression_xp_needed` ломает его немедленно. Его контент переезжает в свою карточку: там `content/progression.json` генерируется и байт-сверяется гейтом.

**Питоновский генератор переживает T0450 и умирает в игровой карточке.** Он —
единственный путь кодогенерации того потребителя (`cmake/GameCodegen.cmake:64-83`);
удалить здесь значит оставить его несобираемым.

### Удаление xp_needed

`progression_xp_needed` возвращает одно число там, где вопрос стал
списочным. Удаляется вместе с `progression_can_level_up`, построенным поверх
него (`progression.c:207`).

Девять мест: `templates/template/src/ui/demo_hud.c:24`,
`templates/template/tests/test_template_composition.c:321`, и у приватного потребителя
`src/ui/upgrades_tree_view.c:226`, `src/ui/trolley_ladder_modal.c:188`,
`src/ui/upgrades_panel_model.h:21`, `src/gameplay/eff_registry.c:184`,
`tests/test_progression.c:168,170`, `tests/test_template_composition.c:219`.
Показываем пока одну позицию, но через `cost_count`/`cost_at`.

### API

```c
progression_track_ref_t progression_track(const char *id);   /* резолв один раз */
float    progression_valuef(progression_track_ref_t, progression_value_t);
float    progression_valuef_at(progression_track_ref_t, progression_value_t, int level);
int64_t  progression_valuei(progression_track_ref_t, progression_value_t);
int64_t  progression_valuei_at(progression_track_ref_t, progression_value_t, int level);
uint32_t progression_cost_count(progression_track_ref_t);
```

`_at` нужен карточке апгрейда для «1.6 -> 1.8» без арифметики в UI. Хэндл
вместо строки убирает линейный `strcmp`-поиск (`progression.c:138-148`).

Несовпадение типа колонки и вызова — **рантайм**, а не сборка: обе функции
берут один `progression_value_t`. Либо различимые типы на класс колонки, либо
не обещать проверку на сборке. Прежняя редакция обещала — снято.

### Законы в README

**Трек хранит только свой вклад; база живёт там, где живёт то, на что
влияют.** Проверка: население в живой игре трогают шесть узлов, своя база у
каждого была бы шестикратной ерундой.

Items **заставляет** авторить строку 1 — значит явно сказать, что она несёт
нулевой вклад, иначе авторы положат туда базу.

### Выдача при достижении уровня

Лид: в первом заходе целиком, включая рантайм. Сегодня `on_level_up`
**запрещён генератором** (`generate_progression_tracks.py:210`), и
`apply_on_level_up` в реальной сборке никогда не исполнялся — значит покрыть
тестами через `templates/template/tests/test_progression_catalog.c`.

Вместе с ним: гейт против `auto`-трека, выдающего на любом уровне ≥
собственной цены того же предмета (иначе бесконечный цикл, ради которого
стоит `PROGRESSION_MAX_LEVELUPS_PER_TRACK`), и решение по каскадам —
`to_track` и рекурсия (`progression.c:131,396-398`) используются или
удаляются здесь же.

Записать: `progression_set_level` (`:271-291`) выдачу **не** прогоняет, прыжок
0→5 пропускает пять уровней; DevAPI и тесты ходят именно через него. Причина
списания захардкожена как `"loot:levelup"` (`:392-394`), а глаголы причин
игро-владельческие — брать из каталога либо записать в `INSTALL.md`.
