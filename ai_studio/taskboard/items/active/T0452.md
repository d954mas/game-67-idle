## What

Add a supported Taskboard CLI operation that reopens an existing archived
item by moving that same item back to its active store.

## Done when

- [ ] `reopen <id>` resolves supported archive locations, including private
      game stores (`--game`, `--store`, qualified id; a Studio/private id
      collision is reported as ambiguous).
- [ ] Pending reopen moves the same file to `active/`, keeping id, created,
      body and history; `quality` is dropped.
- [ ] Sealed reopen copies the head entry to `active/` without touching the
      ZIP and records its batch as `reopened_from: <batch>`.
- [ ] Status defaults to `backlog` (`--status` accepts active statuses only);
      `updated` = today; one `Reopened from <pending|batch>` log line, plus
      `--log` text.
- [ ] After reopen `show`, `list` and `context` see the active task;
      `list --archive` shows one row per id (pending, else the sealed head).
- [ ] Archived copies of an id form one linear chain: a re-closed task seals
      again only when it names the current sealed head; forks, cycles and two
      pending copies are errors, never resolved by order.
- [ ] Errors (unknown id, already active, ambiguous across stores, invalid
      status) write nothing.
- [ ] CLI only (no HTTP route); tests cover pending, sealed, chained re-seal,
      fork/cycle, private store routing and errors; README notes reopen runs
      on the lead's request; the reference describes the chain rule.
