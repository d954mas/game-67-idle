## What

Прогрессии нужно списывать стоимость уровня, которая может состоять из
нескольких предметов. Сегодня она этого сделать не может **атомарно**.

`items_try_pay_cost` принимает непрозрачный `item_cost_ref_t`
(`include/features/items/items.h:13`) — индекс в запечённый каталог, который
выдаёт только сам каталог. Из авторского контента прогрессии такой хэндл не
собрать. Вдобавок вся типизированная секция живёт за
`#if ITEMS_GAME_API_ENABLED || ITEMS_RUNTIME_PACKAGE_ENABLED`
(`items.h:240-243`), а прогрессия пользуется только всегда-доступным
строковым API.

Что ей остаётся — цикл по `items_try_stack_remove_from_container`
(`src/progression.c:238,358`). **Не атомарно**: вторая позиция не прошла, за
первую уже списано. Это тот самый класс отказа, против которого
`progression_level_up` уже закалён (`progression.c:226-235`: слот
аллоцируется до списания, чтобы исчерпание бюджета не сожгло кошелёк).

### Что нужно

Ungated строковый вход:

```c
items_result_t items_try_pay_stacks(
    items_payment_scope_t scope, const char *const *def_ids,
    const int64_t *counts, uint32_t count, const char *reason);
```

### Почему это не обёртка

Планировщик уже двухфазный (`src/items_containers.c:1172-1253`
`build_payment_plan`, `:1255-1266` `apply_payment_plan`), но требования он
перебирает **исключительно** через `items_cost_count`/`items_cost_at` по
непрозрачному хэндлу, а сопоставляет через `entry_matches_item`
(`:1156-1160`). Нужно **расщепить** планировщик на абстрактный источник
требований `{def_id, count}`, где `item_cost_ref_t` — один из адаптеров.

Три вещи, которые легко потерять:

- планировщик поддерживает область из восьми контейнеров
  (`items_payment_scope_t`), а не один — сигнатура обязана это сохранить;
- `items_try_pay_cost` (`:1268-1285`) проверяет `items_reason_check(reason)`
  (`:1270`), `audit_payment_available(reason)` (`:1275`) и шлёт
  `items_emit_payment` (`:1279`); новый вход обязан делать всё три, иначе
  оплата молча обходит аудит;
- планировщик утверждает **пять** условий, которые вызывающий обязан
  обеспечить: непустой список требований (`:1200`), нет неположительных
  количеств (`:1204`), нет переполнения i64 (`:1205-1206`), только
  стековые ресурсы (`:1208-1209`), нет повторов предмета (`:1211-1213`).
  Плюс отказ на повтор контейнера в области (`:1188-1193`).

Два следствия для формы вызова. Прогрессия может платить **только стековыми
ресурсами** — записать это законом. И нулевая цена уровня легальна: такую
позицию надо выбрасывать из списка, а если выброшены все — список пуст и
упирается в ассерт `:1200`. **Назвать, что возвращает пустой список**:
успех «ничего не должен» либо явная ошибка.
