# Физика для прототипа Smash Fest

Рекомендация: взять Box3D первым кандидатом на физику твердых тел, а правила материалов, победы и помощи игроку написать в игре. Собственный 3D solver для этого теста не оправдан. Окончательно фиксировать библиотеку следует после трех проверочных сцен в браузере. В рамках исследования библиотека не собиралась: FPS, размер WASM и стабильность интеграции пока не измерены.

## Основание решения

[Разбор 30 уровней](README.md) показывает падение и вращение отдельных тел, передачу движения между соседями, устойчивые остатки колонн, отскоки шара и разрушение стекла. Для воспроизведения нужны контакты, трение, вращение, устойчивые стопки, непрерывная проверка столкновений быстрого шара и отключение расчета уснувших тел.

В [Smash Fest](https://www.youtube.com/watch?v=mlSaTsozktY) камера преимущественно фронтальная. Это не делает задачу двумерной: тела уходят в глубину и падают с края платформы. В [Knock Fever](https://www.youtube.com/watch?v=2uyJFhlVXuU) глубина особенно заметна по поперечно уложенным вытянутым предметам. Название библиотеки оригиналов по видео определить нельзя. Утверждений об использовании ими PhysX, Jolt или Box3D нет.

| Вариант | Выгода | Цена / неопределенность | Решение |
|---|---|---|---|
| Свой 3D solver | Полный контроль и отсутствие зависимости | Стопки, трение, CCD и устойчивые контакты становятся отдельным проектом | Не писать для быстрого теста |
| Box3D | C17 core, C API, CCD, sleep, convex shapes, события контактов; есть Emscripten-путь | Молодая библиотека, нужна проверка нашей сборки и сцен | Первый кандидат |
| Jolt | Готовая 3D физика, есть официальный JS/WASM-порт | C++ интеграция, собственная цена загрузки и сборки, тоже требует измерений | Запасной вариант при конкретном провале Box3D |
| Упрощенная 2D физика | Можно дешево проверить стрельбу по плоской стенке | Не воспроизводит глубину, сваливание с платформы и поперечные опоры | Только отдельная проверка идеи, с более узким обещанием |

Основание сравнения: [Box3D](https://github.com/erincatto/box3d), [Jolt](https://github.com/jrouwe/JoltPhysics), [JoltPhysics.js](https://github.com/jrouwe/JoltPhysics.js). Это оценка соответствия задаче, не сравнительный benchmark.

## Что известно о Box3D

Это именно Box3D от Erin Catto. [Анонс](https://box2d.org/posts/2026/06/announcing-box3d/) опубликован 30 июня 2026 и называет проект alpha на дату публикации. В проверенном [CMakeLists.txt](https://github.com/erincatto/box3d/blob/main/CMakeLists.txt) указана версия 0.1.0. Эти факты не означают, что любой будущий релиз имеет тот же статус.

[README](https://github.com/erincatto/box3d) описывает C17 core и C API. Верхний CMake-проект включает C и C++; это не означает, что ядро требует переписывания нашей игры на C++. Для игровой интеграции сначала проверяем прямую линковку библиотеки в тот же WASM-модуль, без отдельного JavaScript wrapper.

В [types.h](https://github.com/erincatto/box3d/blob/main/include/box3d/types.h) есть настройка bullet для быстрых тел, параметры трения и упругости, а также события удара. У b3ContactHitEvent есть approachSpeed, точка, нормаль, идентификаторы форм и материалы. Поля impulse в проверенном определении нет. Нельзя строить интеграцию на выдуманном поле события.

Emscripten поддерживается в исходном CMake. Верхняя конфигурация содержит настройки SIMD и pthreads; их нельзя автоматически переносить в требования к игровой странице. Для первого Poki-прототипа предлагается проверить однопоточную сборку. По [документации Emscripten](https://emscripten.org/docs/porting/pthreads.html), потоки требуют соответствующих COOP/COEP-заголовков, а один threaded-бинарник не превращается автоматически в single-thread fallback. Заголовки будущей страницы Poki здесь не проверялись.

## Граница Neotolis

В текущем checkout 623116f0 полноценная физика исключена из scope: [scope.md](../../../../../external/neotolis-engine/docs/spec/core/scope.md). Игровые правила и порядок их исполнения принадлежат игре: [principles.md](../../../../../external/neotolis-engine/docs/spec/core/principles.md). При поиске публичных заголовков готовый rigid-body API не найден.

Поэтому предложение — игровая зависимость и тонкий адаптер тел к трансформам рендера. Engine working tree не изменять. Сначала использовать существующие публичные API Neotolis для сцены, ввода и рендера. Мир и гравитация Y-up; вертикальная гравитация направлена по отрицательному Y.

## Что отдать библиотеке, что оставить игре

| Слой | Ответственность |
|---|---|
| Box3D | Движение шара и предметов, контакты, вращение, трение, упругость, CCD, sleep |
| Игровые материалы | Когда стекло разбивается, какие предметы считаются целью, какие связи разрываются |
| Правила уровня | Лимит шаров, подсчет оставшихся целей, потерянные за платформой цели, победа и проигрыш |
| Представление | Звук, пыль, осколки, экранный отклик, след шара |
| Контент | Положение тел, форма опор, ширина платформы, материалы, стартовый лимит |

Порядок кадра: принять выстрел → выполнить фиксированные шаги физики → прочитать события → накопить решения о разрушении → применить удаления после обработки событий → обновить цели и состояние попытки → отрисовать интерполированные трансформы. Не удалять тела посреди обхода событий с идентификаторами этих тел.

Начальные настройки для проверки: шаг 1/60 секунды и четыре подшага, CCD у шара, простые коллайдеры, sleep у неподвижных конструкций. Это стартовые ручки эксперимента, а не восстановленные параметры оригинала и не гарантированный оптимум.

### Материалы

- Банки и камень в просмотренных эпизодах сохраняют форму, смещаются и падают. Основная обратная связь удара — физическое движение; пыль сама по себе не доказывает разрушение.
- Стекло разбивается и при попадании, и при падении. Для прототипа достаточно порога скорости сближения из события плюс ограничения по материалам. Порог нужно настроить по воспроизводимым сценам; из видео нельзя восстановить массу, HP или точную формулу разрушения.
- Удлиненные группы иногда поворачиваются совместно. Это может быть одно тело с составной геометрией, соединение или движение группы контактов. Не создавать отдельное тело на каждую нарисованную клетку без проверки.
- Мелкие осколки можно оставить визуальным эффектом. Физически важные крупные части моделировать телами. Цели считать по игровым идентификаторам, чтобы мусор не удерживал победу.

После последнего шара требуется дождаться завершения значимого движения: шар способен отскочить и вернуться, опора — упасть с задержкой. Мгновенный проигрыш при нуле боезапаса обрезает результат последнего попадания.

## Три сцены до производства уровней

1. **Стена банок.** Попадание снизу должно локально выбивать опору и обрушивать верх, сохраняя часть боковых колонн. Проверить отскок, отсутствие прохождения шара сквозь тела и отсутствие самостоятельного взрыва стопки.
2. **Балка на двух опорах.** Выбивание одной опоры должно давать понятный поворот и падение; дальнейшее столкновение балки с соседями должно работать без скриптового удаления всей конструкции.
3. **Стеклянная опора под тяжелыми телами.** Удар разбивает опору, верх падает, вторичные столкновения могут разбить другие хрупкие тела. Осколки не мешают завершению уровня.

Проверить native и браузерный вариант на одних исходных сценах, несколько запусков и повтор одинаковых выстрелов. Измерить холодную загрузку, размер сжатой сборки, время физики и кадра на целевом слабом устройстве, количество активных тел, устойчивость покоя, долю случаев пропуска быстрого шара. Допуск между повторениями должен сохранять игровую решаемость, а не обязательно давать побитовую идентичность.

Условие перехода на Jolt — конкретный воспроизводимый дефект или неприемлемая стоимость Box3D в этих сценах, который не устраняется разумной настройкой. Менять solver из-за неподобранной силы выстрела или плохой геометрии опоры рано.

## Быстрый игровой тест

После проверки физики достаточно 10–12 коротких авторских уровней: три обучающих, несколько вариаций опор, введение стекла, две смешанные конструкции, один сложный уровень и облегчение после него. Это предложение для прототипа; полный наблюдаемый набор из 30 уровней сохранен отдельно.

Контент удобно хранить как описание платформы и список экземпляров деталей: тип формы, трансформ, материал, признак цели, при необходимости группа/соединение. Генераторы стен, пирамид, арок и рам помогают создать стартовую конструкцию, но итоговый вариант следует стабилизировать и проверять выстрелами. Полностью случайные стопки не гарантируют интересного решения.

Балансировать в таком порядке:

1. Устойчивость исходной конструкции и понятность слабого места.
2. Скорость, размер и отдача шара; затем контактные свойства материалов.
3. Разница между удачным попаданием, обычным попаданием и промахом.
4. Лимит шаров и количество неприятных добивающих выстрелов.

В исследованном прохождении выигрышные попытки заняли в среднем 8.8 шара; это результат одного игрока и набора уровней, а не норма для аудитории. Запас 20 шаров на ранних уровнях дает свободу экспериментировать. Не начинать с жесткого лимита в 2–4 шара, если проверяется именно удовольствие от обрушения.

Гипотеза мотивации: игрок видит слабое место, делает понятное действие, получает зрелищную цепную реакцию и сразу может попробовать еще раз. Простая стрельба сочетается с локальным мастерством выбора опоры. Это дизайнерская интерпретация наблюдений, не подтвержденная интервью или retention-данными.

Для теста записывать start/win/fail/retry уровня, выстрелы, остаток целей, длительность, момент выхода и длительность финальной уборки. Отдельно наблюдать, пытается ли человек улучшить точку попадания после неудачи и хочет ли следующий уровень. Целевые пороги конверсии следует задавать для конкретного трафика; из этих видео их получить нельзя. Метаигра, магазин и сложная экономика для такой проверки не нужны.
